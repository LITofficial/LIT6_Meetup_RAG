## 발표 주제

이번 발표의 주제는 **Microsoft Foundry를 사용하여 사용자 고유의 데이터로 RAG 기반 솔루션 개발**입니다.

생성형 AI를 실제 업무에 적용할 때 중요한 질문은 "어떤 모델을 쓸 것인가"에서 끝나지 않습니다. 더 중요한 질문은 다음과 같습니다.

```text
AI가 어떤 데이터를 근거로 답변하게 만들 것인가?
```

Microsoft Foundry는 AI 앱과 에이전트를 만들고, 모델을 배포하고, 도구와 데이터를 연결할 수 있는 통합 플랫폼입니다. 이 발표에서는 Foundry를 중심으로 사용자가 가진 문서와 데이터를 검색 가능한 지식으로 만들고, 그 지식을 모델 응답에 연결하는 RAG 구조를 설명합니다.

핵심 메시지는 단순합니다.

> RAG 솔루션의 품질은 모델만으로 결정되지 않습니다. 사용자의 데이터를 어떻게 수집, 인덱싱, 검색, 검증하느냐가 함께 결정합니다.

# 서론

## 1. 왜 사용자 고유 데이터가 필요한가

일반적인 LLM은 자연스러운 답변을 만들 수 있습니다. 하지만 우리 회사의 내부 규정, 제품 매뉴얼, 프로젝트 문서, 회의록, 고객 지원 이력, 교육 자료 같은 데이터까지 자동으로 알고 있지는 않습니다.

예를 들어 다음과 같은 질문은 공개 지식만으로는 정확히 답하기 어렵습니다.

```text
우리 팀의 장비 반납 절차를 알려줘.
```

```text
지난 분기 프로젝트 회고에서 나온 개선 항목을 정리해줘.
```

```text
우리 제품의 최신 설치 가이드 기준으로 오류 해결 방법을 알려줘.
```

이런 질문에 답하려면 모델이 일반 지식이 아니라 **사용자가 제공한 실제 데이터**를 참고해야 합니다.

## 2. 일반 LLM만 사용할 때의 한계

일반 LLM만 사용하면 답변은 자연스러울 수 있지만 업무 적용에는 한계가 있습니다.

| 기대하는 것 | 일반 LLM만 사용할 때의 한계 |
| --- | --- |
| 내부 문서 기반 답변 | 모델이 해당 문서를 알지 못함 |
| 최신 자료 반영 | 학습 이후 변경된 내용을 반영하기 어려움 |
| 출처 확인 | 어떤 문서를 근거로 답했는지 검증하기 어려움 |
| 조직별 절차 안내 | 공개 데이터에 없는 업무 지식은 부족함 |
| 신뢰 가능한 자동화 | 그럴듯하지만 실제와 다른 답변이 나올 수 있음 |

따라서 업무용 AI에서는 모델에게 모든 것을 외우게 만드는 방식보다, 필요한 시점에 관련 데이터를 검색해 답변에 활용하는 방식이 더 현실적입니다.

## 3. 발표에서 해결하려는 문제

이번 발표는 다음 질문에 답하는 것을 목표로 합니다.

```text
내 문서와 데이터를 AI가 참고하게 만들려면 어떤 구조가 필요할까?
```

```text
Microsoft Foundry에서는 RAG 솔루션을 어떤 구성 요소로 만들 수 있을까?
```

```text
검색, 모델, 에이전트를 어떻게 연결해야 RAG 솔루션을 만들 수 있을까?
```

결론부터 말하면 필요한 것은 단순한 챗봇이 아니라 **사용자 데이터와 연결된 검색 기반 생성 시스템**입니다.

# 본론

## 1. RAG란 무엇인가

RAG는 **Retrieval-Augmented Generation**의 약자이며, 한국어로는 보통 **검색 증강 생성**이라고 설명합니다.

단계를 나누면 다음과 같습니다.

```text
Retrieval
  -> 질문과 관련된 정보를 외부 데이터에서 검색

Augmented
  -> 검색 결과를 모델 입력에 보강

Generation
  -> 보강된 정보를 바탕으로 답변 생성
```

즉, RAG는 모델이 기억에만 의존해서 답변하는 방식이 아닙니다. 먼저 사용자의 데이터에서 관련 내용을 찾고, 그 내용을 모델에게 함께 전달해 답변을 생성하게 합니다.

기본 흐름은 다음과 같습니다.

```text
사용자 질문
  -> 관련 문서 검색
  -> 검색 결과를 모델 컨텍스트에 포함
  -> 모델이 근거 기반 답변 생성
  -> 답변과 출처 반환
```

이 방식의 장점은 모델을 다시 학습시키지 않고도 새로운 문서, 최신 정책, 조직별 지식을 답변에 활용할 수 있다는 점입니다.

## 2. Microsoft Foundry의 역할

Microsoft Foundry는 AI 앱과 에이전트를 만들기 위한 통합 플랫폼입니다. Foundry 안에서 프로젝트를 만들고, 모델을 배포하고, 도구와 데이터 원본을 연결할 수 있습니다.

RAG 관점에서 Foundry의 역할은 다음과 같습니다.

| 구성 요소 | 역할 |
| --- | --- |
| Foundry 프로젝트 | 모델, 데이터, 도구를 묶어 관리 |
| Foundry Models | 답변 생성을 수행할 모델 배포 |
| Vector index | 문서와 데이터를 검색 가능한 벡터 인덱스로 구성 |
| Azure AI Search | 대규모 문서 검색, 벡터 검색, 하이브리드 검색 지원 |
| Foundry Agent Service | 데이터와 도구를 사용하는 에이전트 구성 |

이 발표에서는 Foundry를 단순한 모델 실행 환경이 아니라 **RAG 솔루션을 개발하는 작업 공간**으로 다룹니다.

## 3. RAG 처리 과정

Microsoft Foundry에서 사용자 고유 데이터 기반 RAG 솔루션은 크게 세 단계로 이해할 수 있습니다.

```text
사용자 데이터 연결
  -> 인덱싱과 검색
  -> 근거 기반 답변 생성
```

## 3-1. 사용자 데이터 연결

RAG 솔루션의 시작점은 모델이 아니라 데이터입니다. 사용자가 가진 PDF, Word 문서, FAQ, 업무 매뉴얼, 회의록, 제품 문서, 데이터베이스 같은 자료를 Foundry에서 사용할 수 있는 데이터 원본으로 연결해야 합니다.

데이터는 로컬 파일, Azure Blob Storage, 기존 Azure AI Search 인덱스, Foundry 데이터 자산 등에서 가져올 수 있습니다. 중요한 점은 문서를 단순히 저장하는 것이 아니라, AI가 검색해서 사용할 수 있는 지식 원본으로 준비하는 것입니다.

## 3-2. 인덱싱과 검색

연결된 데이터는 그대로 모델에 넣기 어렵습니다. 먼저 문서에서 텍스트를 추출하고, 의미 있는 작은 조각으로 나누고, 질문과 비교할 수 있도록 임베딩을 만들어 벡터 인덱스에 저장합니다.

```text
문서 원본
  -> 텍스트 추출
  -> 청크 분할
  -> 임베딩 생성
  -> 벡터 인덱스 저장
```

사용자가 질문하면 Foundry는 인덱스에서 질문과 관련된 문서 조각을 찾습니다. 이때 정확한 키워드만 찾는 것이 아니라, 의미가 비슷한 내용도 찾을 수 있습니다. 그래서 사용자가 문서의 정확한 제목이나 표현을 몰라도 관련 정보를 검색할 수 있습니다.

## 3-3. 근거 기반 답변 생성

검색 결과가 준비되면 모델은 그 내용을 근거로 답변을 생성합니다. 즉, 모델이 혼자 기억에 의존해서 답하는 것이 아니라, 인덱스에서 찾은 문서 조각을 함께 보고 답변합니다.

```text
사용자 질문
  -> 인덱스에서 관련 청크 검색
  -> 검색 결과와 출처를 모델 입력에 포함
  -> 모델이 답변 생성
  -> 답변과 참고 문서 반환
```

이때 핵심 원칙은 세 가지입니다. 검색된 근거를 우선 사용하고, 근거에 없는 내용은 추측하지 않으며, 답변에 참고 문서나 출처를 함께 표시하는 것입니다.

## 4. Foundry Agent Service로 확장

단순 질의응답을 넘어서면 에이전트 구조가 필요할 수 있습니다.

Foundry Agent Service를 사용하면 모델이 데이터 원본뿐 아니라 도구와 작업 흐름을 함께 사용할 수 있습니다.

예를 들어 다음과 같은 확장이 가능합니다.

- 문서 검색 후 답변 생성
- 답변에 출처와 요약 포함
- 필요한 경우 특정 API 호출
- 사용자 권한에 따라 검색 범위 제한
- 여러 도구를 조합해 업무 흐름 자동화

즉, RAG는 "문서 기반 답변"의 출발점이고, 에이전트는 그 위에서 실제 업무 행동까지 확장하는 구조입니다.

## 5. 전체 아키텍처

Microsoft Foundry를 중심으로 한 RAG 솔루션의 전체 흐름은 다음과 같습니다.

```text
[사용자 고유 데이터]
  PDF / DOCX / FAQ / 매뉴얼 / 회의록 / DB
        |
        v
[데이터 수집 및 저장]
  로컬 파일 / Blob Storage / Foundry 데이터 / 기존 Search 인덱스
        |
        v
[인덱싱]
  텍스트 추출, 청크 분할, 임베딩 생성, 메타데이터 구성
        |
        v
[검색 계층]
  Vector index / Azure AI Search / 하이브리드 검색
        |
        v
[Microsoft Foundry]
  프로젝트, 모델 배포, 도구 연결, 에이전트 구성
        |
        v
[RAG 응답]
  검색된 근거 기반 답변, 출처, 후속 질문
```

이 구조에서 중요한 점은 모델과 데이터가 분리되어 있다는 것입니다. 데이터는 계속 업데이트되고, 인덱스는 최신 데이터를 반영하며, 모델은 질문 시점에 검색된 근거를 바탕으로 답변합니다.

## 6. 데모 시나리오

데모의 목표는 Microsoft Foundry 환경을 처음 구성하는 단계부터 시작해, 사용자가 제공한 문서가 최종 답변의 근거로 사용되는 결과까지 확인하는 것입니다.

```text
1. Microsoft Foundry 포털에 접속한다.
2. Foundry 리소스와 프로젝트를 생성한다.
3. 사용할 모델을 선택하고 배포한다.
4. 데모용 문서 데이터를 준비한다.
5. 문서 데이터를 업로드하거나 데이터 원본에 연결한다.
6. 벡터 인덱스를 생성한다.
7. 인덱스가 생성된 문서를 확인한다.
8. 질문을 입력해 검색과 답변 생성을 실행한다.
9. 답변에 사용된 근거와 출처를 확인한다.
10. 최종적으로 문서 기반 RAG 응답이 만들어지는 결과를 확인한다.
```

## 6-1. 데모에서 강조할 포인트

- 모델이 일반 지식만으로 답하지 않는다는 점
- 사용자가 제공한 문서가 검색 대상이 된다는 점
- 질문과 관련된 문서 조각이 먼저 검색된다는 점
- 검색 결과가 모델 응답의 근거로 사용된다는 점
- 답변에 출처를 포함해 검증 가능성을 높일 수 있다는 점
- 문서가 업데이트되면 인덱스 갱신을 통해 답변도 최신화할 수 있다는 점

# 결론

Microsoft Foundry를 사용한 RAG 솔루션의 핵심은 모델을 단독으로 사용하는 것이 아니라, 사용자가 가진 데이터를 검색 가능한 지식으로 만들고 그 지식을 모델 응답에 연결하는 것입니다.

생성형 AI가 업무에 의미 있게 쓰이려면 답변이 자연스러운 것만으로는 부족합니다.

> 중요한 것은 AI가 사용자의 실제 데이터를 근거로 답변하고, 그 근거를 사용자가 확인할 수 있어야 한다는 점입니다.

Foundry는 이 흐름을 프로젝트, 모델, 인덱스, 에이전트의 관점에서 하나의 개발 경험으로 묶어줍니다. 따라서 RAG 솔루션을 만들 때는 모델 선택뿐 아니라 데이터 준비, 인덱싱, 검색 품질, 출처 표시까지 함께 설계해야 합니다.
