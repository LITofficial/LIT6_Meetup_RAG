## 발표 주제

이번 발표의 주제는 **ChatGPT, Gemini, NotebookLM처럼 PDF를 올리고 질문하는 기능의 내부 원리를 LangChain과 Gemini API로 직접 구현해보는 것**입니다.

요즘 AI 서비스에서는 PDF 업로드와 문서 기반 질의응답 기능이 점점 흔해지고 있습니다. 사용자 입장에서는 파일을 올리고 질문하면 끝이지만, 개발자 입장에서는 그 뒤에 중요한 질문이 남습니다.

```text
PDF는 어떻게 검색 가능한 데이터로 바뀌고, AI는 그중 어떤 내용을 보고 답하는 걸까?
```

이 발표에서는 완성된 AI 서비스의 사용법을 소개하는 대신, LangChain을 중심으로 PDF 텍스트 추출, 청킹, 임베딩, 검색, 프롬프트 조립, Gemini 답변 생성 과정을 직접 구현합니다.

핵심 메시지는 단순합니다.

> RAG는 AI가 문서를 외우게 만드는 기술이 아니라, 질문에 필요한 근거를 찾아서 답변하게 만드는 구조입니다.

# 서론

## 1. 우리는 이미 문서 기반 AI를 써본 적이 있다

요즘은 PDF나 문서를 AI에 올리고 질문하는 일이 익숙해졌습니다. Gemini, ChatGPT, NotebookLM 같은 서비스에 강의자료, 논문, 매뉴얼, 과제 안내문을 올리고 다음과 같이 물어볼 수 있습니다.

```text
이 문서에서 핵심 내용을 요약해줘.
```

```text
시험에 나올 만한 개념을 정리해줘.
```

```text
이 자료에서 제출 조건만 뽑아줘.
```

사용자 입장에서는 매우 간단합니다. 문서를 올리고 질문하면 AI가 답변해줍니다.

하지만 개발자 입장에서 보면 여기서 중요한 질문이 생깁니다.

```text
AI는 문서 전체를 어떻게 읽고, 질문과 관련된 부분을 어떻게 찾아서 답하는 걸까?
```

이 질문에서 출발하는 구조가 바로 RAG입니다.

## 2. 그럼 그냥 NotebookLM을 쓰면 안 될까?

자연스럽게 이런 생각이 들 수 있습니다.

```text
그냥 NotebookLM 같은 완성형 서비스를 쓰면 되는 것 아닌가?
```

맞습니다. NotebookLM도 문서를 업로드하고 질문하면 답변해주는 완성형 RAG 서비스라고 볼 수 있습니다. 개인이 문서를 빠르게 읽고 정리하는 용도라면 충분히 좋은 도구입니다.

하지만 기업 환경에서는 요구사항이 달라집니다. 기업은 단순히 문서를 읽고 요약하는 것을 넘어서, 내부 시스템과의 연결, 사용자 권한, 보안 정책, 검색 방식, 답변 정책까지 직접 통제해야 합니다.

그래서 중견기업이나 대기업에서는 완성형 서비스를 그대로 쓰기보다, 조직의 데이터와 정책에 맞게 설계한 커스텀 RAG가 필요합니다.

## 3. 기업에서는 왜 커스텀 RAG가 필요할까?

커스텀 RAG를 만들면 기업 환경에 맞는 문서 기반 AI를 설계할 수 있습니다.

1. 다양한 시스템과 연동할 수 있습니다.

GitHub, Slack, SharePoint, 사내 DB, ERP 등 기업 내부 시스템과 연결할 수 있습니다.

2. 권한 기반 검색이 가능합니다.

사용자 권한에 따라 조회 가능한 문서만 검색되도록 만들 수 있고, 부서별 접근 제어도 적용할 수 있습니다.

3. 프롬프트를 커스터마이징할 수 있습니다.

답변 스타일, 출처 표시, 추측 금지, 특정 문서 우선 검색 같은 정책을 기업 요구사항에 맞게 반영할 수 있습니다.

4. 검색 구조를 직접 설계할 수 있습니다.

Vector Search, Hybrid Search, Reranking, Chunk 전략 등을 목적에 맞게 최적화할 수 있습니다.

5. 기업 환경에 맞게 확장할 수 있습니다.

보안 정책, 로그 관리, 감사 추적, 업무 자동화와 연결할 수 있습니다.

정리하면 다음과 같습니다.

```text
커스텀 RAG는 기업 환경에 맞춰 데이터 연결, 권한 관리, 검색 방식, 프롬프트 정책을 자유롭게 설계할 수 있다는 장점이 있습니다.
```

## 4. 그래서 RAG 구조를 알아야 한다

커스텀 RAG를 만들려면 단순히 AI API를 호출하는 것만으로는 부족합니다. 문서를 어떻게 나누고, 어떤 방식으로 임베딩하고, 질문과 관련된 내용을 어떻게 검색하고, 검색된 근거를 어떤 프롬프트로 조립할지 이해해야 합니다.

즉, RAG를 공부한다는 것은 단순히 PDF 질의응답 기능을 따라 만드는 것이 아닙니다. 완성형 서비스 뒤에서 동작하는 데이터 흐름을 이해하고, 나중에 우리 조직이나 서비스에 맞는 문서 기반 AI를 직접 설계할 수 있게 되는 것입니다.

## 5. 이번 발표에서 확인할 것

이번 발표에서는 LangChain과 Gemini를 사용해 간단한 RAG 파이프라인을 직접 구현해봅니다.

목표는 완성된 NotebookLM 같은 서비스를 다시 만드는 것이 아닙니다. 대신 다음 과정을 직접 확인하는 것입니다.

```text
문서 업로드
  -> 텍스트 추출
  -> 청크 분할
  -> 임베딩 생성
  -> 질문과 관련된 청크 검색
  -> 검색된 근거를 프롬프트에 포함
  -> Gemini가 근거 기반 답변 생성
```

이 과정을 보면 문서 기반 AI가 단순히 PDF를 모델에 넣는 기능이 아니라, 문서를 검색 가능한 지식으로 바꾸고 필요한 근거만 찾아 답변에 연결하는 구조라는 것을 이해할 수 있습니다.

# 본론

## 1. RAG란 무엇인가

RAG는 **Retrieval-Augmented Generation**의 약자이며, 한국어로는 보통 **검색 증강 생성**이라고 설명합니다.

LLM은 질문을 받으면 내부 지식을 바탕으로 답변을 생성합니다. 하지만 사용자가 방금 업로드한 PDF의 세부 내용, 최신 공지, 특정 문서의 조건은 모델이 원래 알고 있던 지식이 아닐 수 있습니다.

그래서 RAG는 모델에게 바로 질문을 던지지 않습니다. 먼저 문서에서 질문과 관련된 근거를 찾고, 그 근거를 질문과 함께 모델 입력에 넣습니다. 모델은 혼자 기억해서 답하는 것이 아니라, 검색된 문서 조각을 참고해 답변합니다.

단계를 나누면 다음과 같습니다.

```text
Retrieval
  -> 질문과 관련된 정보를 외부 데이터에서 검색

Augmented
  -> 검색 결과를 모델 입력에 보강

Generation
  -> 보강된 정보를 바탕으로 답변 생성
```

즉, RAG는 업로드된 문서를 그대로 모델에게 던지는 방식이 아닙니다. 먼저 문서에서 질문과 관련된 내용을 찾고, 그 내용을 모델에게 함께 전달해 답변을 생성하게 합니다.

기본 흐름은 다음과 같습니다.

```text
사용자 질문
  -> 관련 문서 검색
  -> 검색 결과를 모델 컨텍스트에 포함
  -> 모델이 근거 기반 답변 생성
  -> 답변과 출처 반환
```

이 방식의 장점은 모델을 다시 학습시키지 않고도 새로 업로드한 강의자료, 논문, 과제 안내문 같은 문서를 답변에 활용할 수 있다는 점입니다.

## 2. RAG 처리 과정

RAG 처리 과정은 길게 설명하면 복잡해 보이지만, 핵심은 이겁니다.

```text
문서를 읽는다
  -> 작게 나눈다
  -> 의미를 숫자로 바꾼다
  -> 질문과 가까운 조각을 찾는다
  -> 찾은 근거로 답변한다
```

즉, RAG는 PDF 전체를 Gemini에게 한 번에 던지는 구조가 아닙니다. 먼저 문서를 검색 가능한 형태로 바꾸고, 사용자의 질문과 관련 있는 부분만 골라서 모델에게 전달합니다.

## 2-1. 문서를 읽을 수 있는 텍스트로 바꾸기

RAG 솔루션의 시작점은 모델이 아니라 문서입니다. 사용자가 가진 강의자료, 논문, 과제 안내문, 매뉴얼 같은 PDF를 AI가 처리할 수 있는 텍스트로 변환해야 합니다.

이 단계의 핵심은 PDF를 "업로드된 파일"이 아니라 "검색할 수 있는 텍스트 데이터"로 바꾸는 것입니다. PDF 안의 문장을 꺼내고, 불필요한 공백을 정리하고, 나중에 출처를 표시할 수 있도록 파일명과 제목 같은 정보도 함께 보관합니다.

```text
업로드된 PDF
  -> 텍스트 추출
  -> 파일명과 제목 보관
  -> 검색 원본 데이터 생성
```

여기서 한 가지 한계도 함께 짚으면 좋습니다. 이미지로만 된 스캔 PDF나 복잡한 표는 단순 텍스트 추출만으로 잘 읽히지 않을 수 있습니다. 실제 서비스라면 OCR이나 표 분석 같은 처리가 추가될 수 있습니다.

## 2-2. 긴 문서를 작은 청크로 나누기

긴 PDF 전체를 한 번에 모델에게 넘기면 비효율적이고, 질문과 상관없는 내용까지 같이 들어갑니다. 그래서 문서를 의미 있는 작은 조각, 즉 청크로 나눕니다.

```text
경북대학교 졸업요건 및 학칙 자료
  -> [청크 1: 총 이수학점 기준]
  -> [청크 2: 전공/교양 이수 요건]
  -> [청크 3: 졸업논문 또는 졸업작품 규정]
```

청킹의 목적은 문서를 잘게 쪼개는 것 자체가 아닙니다. 질문이 들어왔을 때 전체 문서가 아니라 관련 있는 조각만 찾을 수 있게 만드는 것입니다.

## 2-3. 청크를 임베딩으로 바꾸기

청크를 만들었다면 각 청크를 임베딩으로 바꿉니다. 임베딩은 텍스트의 의미를 숫자 좌표로 표현한 값입니다.

```text
[청크: 졸업을 위해서는 학과별 전공 이수학점과 교양 이수 요건을 모두 충족해야 합니다]
  -> [0.12, -0.44, 0.31, 0.08, ...]
```

이렇게 숫자로 바꿔두면 문장끼리 의미가 얼마나 가까운지 계산할 수 있습니다. 단순히 같은 단어가 있는지 찾는 것이 아니라, 질문과 의미가 가까운 문서 조각을 찾을 수 있게 됩니다.

## 2-4. 질문과 가까운 청크 검색하기

사용자가 질문하면 질문도 임베딩으로 바꿉니다. 그리고 질문 임베딩과 문서 청크 임베딩을 비교해 가장 가까운 청크를 찾습니다.

```text
사용자 질문: "총 학점만 채우면 졸업할 수 있어?"
  -> 질문 임베딩 생성
  -> 문서 청크들과 비교
  -> "총 이수학점 기준", "전공/교양 이수 요건", "졸업논문 또는 졸업작품 규정" 청크 선택
```

여기서 중요한 점은 모델에게 모든 문서를 넘기지 않는다는 것입니다. 먼저 검색을 통해 관련 있는 청크만 고르고, 그 조각만 답변 생성에 사용합니다.

## 2-5. 검색된 근거로 답변 생성하기

마지막으로 검색된 청크와 사용자 질문을 함께 Gemini에게 전달합니다. 이때 모델에게 중요한 규칙을 줍니다.

```text
1. 검색된 근거만 사용한다.
2. 근거에 없는 내용은 추측하지 않는다.
3. 답변 마지막에 출처를 표시한다.
```

그래서 최종 답변은 모델의 일반 지식만으로 만들어진 문장이 아니라, 방금 검색된 문서 조각을 근거로 한 답변이 됩니다.

```text
총 이수학점만 채웠다고 해서 바로 졸업 요건을 모두 충족하는 것은 아닙니다.
전공 이수학점, 교양 이수 요건, 졸업논문 또는 졸업작품, 학과별 추가 요건을 함께 확인해야 합니다.

출처: 경북대학교 졸업요건 및 학칙 자료
```

발표에서 이 파트를 정리할 때는 다음 한 문장으로 말하면 됩니다.

```text
RAG는 문서를 외우게 하는 기술이 아니라, 질문에 필요한 근거를 찾아서 답변에 붙여주는 구조입니다.
```

## 3. 왜 직접 구현해보는가

이 데모는 NotebookLM 같은 완성된 서비스를 사용하는 대신 RAG 흐름을 직접 구현합니다. 이유는 문서 기반 AI의 내부 흐름을 숨기지 않고 보여주기 위해서입니다.

직접 구현하면 다음 과정을 명확히 확인할 수 있습니다.

- PDF에서 어떤 텍스트가 추출되는지
- 텍스트가 어떤 청크로 나뉘는지
- 청크마다 어떤 임베딩이 만들어지는지
- 질문과 가장 가까운 청크가 어떻게 선택되는지
- 검색 결과가 어떤 프롬프트로 조립되는지
- Gemini가 어떤 근거를 바탕으로 답변하는지

즉, 이 프로젝트의 목적은 완성된 PDF 질의응답 서비스를 사용하는 것이 아니라, 그 기능이 실제로 어떤 데이터 흐름으로 동작하는지 직접 확인하는 것입니다.

## 4. 데모 시나리오

데모에서는 학생들이 실제로 궁금해할 만한 PDF를 사용합니다. 예시는 **"경북대학교 졸업요건 및 학칙 자료"** 문서입니다.

데모는 React 프론트엔드와 FastAPI 백엔드로 구성되어 있으며, LangChain이 RAG 흐름을 연결하고 Gemini가 최종 답변을 생성합니다.

이 문서에는 다음과 같은 내용이 들어 있다고 가정합니다.

- 총 이수학점 기준
- 전공, 교양, 일반선택 이수 요건
- 졸업논문, 졸업작품, 졸업시험 관련 규정
- 복수전공, 부전공, 전과 학생의 졸업요건
- 학칙상 졸업 제한 조건과 예외 처리
- 학과별 추가 졸업요건과 확인 절차

데모에 들어가기 전에는 청중에게 질문 후보를 보여주고 하나를 고르게 합니다.

```text
1. 총 학점만 채우면 졸업할 수 있어?
2. 전공, 교양, 졸업작품 중에서 꼭 확인해야 할 조건은 뭐야?
3. 복수전공을 하면 원래 전공 졸업요건은 어떻게 달라져?
4. 학점은 다 채웠는데도 졸업이 안 될 수 있는 경우가 있어?
```

이 중 하나를 선택한 뒤, 선택한 질문이 PDF 안의 어떤 청크와 연결되는지 데모에서 확인합니다.

## 4-1. 데모 화면 구성

| 영역 | 표시 내용 |
| --- | --- |
| 상단 | PDF 업로드, 프롬프트 입력, Run RAG 버튼 |
| 왼쪽 | RAG 단계 목록 |
| 중앙 | 데이터 패킷이 단계별로 이동하는 파이프라인 |
| 하단 | 각 단계의 Input / Output |
| 결과 영역 | Gemini 답변과 출처 파일명 |

데모의 목표는 사용자가 제공한 PDF가 최종 답변의 근거로 사용되는 과정을 프론트엔드에서 단계별로 확인하는 것입니다.

```text
1. "경북대학교 졸업요건 및 학칙 자료" PDF를 업로드한다.
2. 졸업 가능 여부를 판단할 때 확인해야 할 조건을 묻는 질문을 입력한다.
3. 백엔드가 PDF에서 텍스트를 추출한다.
4. 총 이수학점, 전공/교양 요건, 졸업작품, 학칙상 제한 조건이 청크로 나뉜다.
5. 각 청크의 임베딩이 생성된다.
6. 질문과 관련 있는 청크가 검색된다.
7. 검색 결과와 질문이 프롬프트로 조립된다.
8. Gemini API가 문서 근거 기반 답변을 생성한다.
9. 프론트엔드에서 각 단계의 입력과 출력을 확인한다.
10. 최종 답변과 출처를 확인한다.
11. 화면에서 본 단계가 백엔드 코드의 어느 부분과 연결되는지 확인한다.
```

데모가 끝나면 사용자는 다음 결과를 확인할 수 있습니다.

```text
경북대학교 졸업요건 및 학칙 자료를 기준으로 졸업을 위해 확인해야 할 조건이 정리된다.
답변에 사용된 관련 청크와 출처 파일명이 함께 표시된다.
청크가 임베딩으로 바뀌고 검색 결과가 프롬프트에 들어가는 과정을 볼 수 있다.
```

## 4-2. 데모에서 확인할 코드

데모 중에는 전체 코드를 모두 설명하지 않고, 화면에서 본 RAG 흐름과 직접 연결되는 코드만 짚습니다.

1. `document_from_upload`
   - 업로드된 PDF를 읽고 페이지별 텍스트를 추출합니다.
2. `build_langchain_documents`
   - 추출된 텍스트를 LangChain `Document` 객체로 바꿉니다.
3. `split_documents_with_langchain`
   - LangChain `RecursiveCharacterTextSplitter`로 긴 문서를 작은 청크로 나눕니다.
4. `build_vector_store`
   - LangChain `GoogleGenerativeAIEmbeddings`로 각 청크를 비교 가능한 벡터로 바꿉니다.
5. `retrieve`
   - 사용자 질문과 의미적으로 가까운 청크를 찾습니다.
6. `build_prompt`
   - LangChain `ChatPromptTemplate`으로 검색된 청크와 사용자 질문을 프롬프트로 조립합니다.
7. `generate_answer_with_gemini`
   - LangChain `ChatGoogleGenerativeAI`를 호출해 최종 답변을 생성합니다.

코드 설명의 목표는 문법 설명이 아니라, 화면에서 보인 단계가 실제 코드의 어느 부분에서 실행되는지 확인하는 것입니다.

## 4-3. 데모 해석

데모가 끝난 뒤에는 결과 화면을 바로 넘기지 않고, 방금 본 흐름을 다시 짚습니다.

```text
질문이 바로 Gemini로 간 것이 아닙니다.
먼저 PDF가 여러 청크로 나뉘고,
각 청크가 임베딩으로 바뀌고,
질문과 가까운 청크가 검색되고,
그 검색 결과가 프롬프트에 들어간 뒤,
Gemini가 답변을 생성했습니다.
```

이 해석 파트에서 강조할 부분은 다음과 같습니다.

- 청크 수와 임베딩 수가 1:1로 연결된다는 점
- 검색 단계에서 모든 문서가 아니라 관련 청크만 선택된다는 점
- 프롬프트 단계에서 검색 결과가 모델 입력으로 들어간다는 점
- 최종 답변은 모델의 일반 지식만이 아니라 검색된 근거를 바탕으로 생성된다는 점

## 4-4. 데모에서 강조할 포인트

- 완성된 PDF 질의응답 서비스의 내부 원리를 직접 볼 수 있다는 점
- 사용자가 제공한 PDF가 검색 가능한 데이터로 바뀐다는 점
- 질문과 관련된 문서 조각이 먼저 검색된다는 점
- 청크 수와 임베딩 수가 1:1로 연결된다는 점
- 검색 결과가 Gemini 응답의 근거로 사용된다는 점
- 답변에 출처를 포함해 검증 가능성을 높일 수 있다는 점
- 프론트엔드에서 RAG 단계별 데이터 이동을 시각적으로 확인할 수 있다는 점

## 4-5. 이 데모의 한계

이 데모가 ChatGPT, Gemini, NotebookLM의 실제 내부 구현과 같다는 의미는 아닙니다. 상용 서비스는 더 복잡한 PDF 파싱, 표와 이미지 처리, 긴 컨텍스트 처리, 재랭킹, 캐싱, 권한 관리 등을 사용할 수 있습니다.

또한 이 데모는 학습용 구조이기 때문에 임베딩과 검색 과정이 단순화되어 있습니다. 실제 서비스라면 더 좋은 임베딩 모델, 벡터 데이터베이스, 검색 결과 재정렬, 표와 이미지 처리, 사용자별 접근 권한 관리가 필요할 수 있습니다.

하지만 RAG의 핵심 흐름인 문서 처리, 청킹, 임베딩, 검색, 프롬프트 조립, 답변 생성은 이 데모만으로도 확인할 수 있습니다. 이 프로젝트의 목적은 실제 서비스를 복제하는 것이 아니라, 문서 기반 질의응답을 이해하기 위한 대표적인 RAG 구조를 단순화해 구현해보는 것입니다.

# 결론

LangChain과 Gemini를 사용한 RAG 솔루션의 핵심은 PDF를 단순히 업로드하는 것이 아니라, 문서를 검색 가능한 지식으로 만들고 그 지식을 모델 응답에 연결하는 것입니다.

생성형 AI가 학습 도구로 의미 있게 쓰이려면 답변이 자연스러운 것만으로는 부족합니다.

> 중요한 것은 AI가 사용자의 실제 데이터를 근거로 답변하고, 그 근거를 사용자가 확인할 수 있어야 한다는 점입니다.

LangChain은 이 흐름을 문서 처리, 검색, 프롬프트 조립, 모델 호출의 관점에서 코드로 연결할 수 있게 해줍니다. Gemini는 검색된 근거를 바탕으로 최종 답변을 생성합니다.

따라서 RAG 솔루션을 만들 때는 모델 선택뿐 아니라 문서 처리, 청킹 방식, 임베딩, 검색 품질, 프롬프트 설계, 출처 표시까지 함께 설계해야 합니다.

이번 데모는 하나의 PDF에서 시작하지만, 같은 구조는 여러 문서와 폴더 단위 검색으로 확장할 수 있습니다. 강의자료 검색 도우미, 논문 요약 비서, 과제 안내문 Q&A, 개인 지식 검색기처럼 발전시킬 수 있습니다.
